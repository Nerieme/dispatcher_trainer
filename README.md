Лабораторная работа 1: настройка рабочей конфигурации C++17/20.

## Среда
Основной вариант: VS Code + Docker Dev Container.
Альтернативный вариант: Linux в VirtualBox.

## Как открыть проект
1. Установить VS Code, Docker и расширение Dev Containers.
2. Открыть каталог проекта в VS Code.
3. Выполнить команду: Dev Containers: Reopen in Container.

## Сборка вручную
```bash
cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
./build/debug/dispatcher_trainer_lab1
```

## Сборка в VS Code
1. CMake: Configure
2. CMake: Build
3. CMake: Run Without Debugging
4. Run and Debug → Debug CMake target with CodeLLDB

## Проверено

## Контрольные вопросы
1. Зачем в данной лабораторной работе Docker Dev Container выбран основной рабочей средой?

Чтобы обеспечить всем студентам одинаковое, воспроизводимое окружение независимо от их ОС (Windows, Linux, macOS). В контейнере фиксируются версии компилятора, CMake, clangd и отладчика, что снижает вероятность ошибок «у меня не собирается, а у соседа собирается» и готовит к последующей инженерной работе.

2. Чем контейнер отличается от виртуальной машины VirtualBox с точки зрения учебной разработки?

Контейнер использует ядро хоста и изолирует только пользовательское пространство, поэтому он легче, быстрее запускается и потребляет меньше ресурсов. Виртуальная машина эмулирует полноценное железо и запускает свою ОС, что даёт полную изоляцию, но требует больше ресурсов и времени на настройку. В курсе VM — это резервный вариант, если Docker недоступен.

3. Какие файлы входят в минимальную конфигурацию .devcontainer?

Два основных файла: Dockerfile (описание образа и устанавливаемых пакетов) и devcontainer.json (настройки VS Code: какие расширения ставить, рабочая папка, пользователь, команды после создания).

4. Почему расширения CMake Tools, clangd и CodeLLDB должны быть доступны внутри контейнерного контекста?

Потому что именно внутри контейнера находятся компилятор, CMake и отладчик. Если расширения работают на стороне основной ОС, они не смогут корректно взаимодействовать с инструментами контейнера (например, clangd не увидит compile_commands.json, а CodeLLDB не запустит отладчик внутри Linux-среды).

5. Как проверить, что терминал VS Code открыт именно внутри контейнера?

Выполнить команду pwd (путь должен начинаться с /workspaces/...), whoami (обычно пользователь vscode), а также посмотреть в левый нижний угол VS Code — там должен быть индикатор Dev Container.

6. Для чего нужен файл CMakeLists.txt?

Это описание структуры сборки для CMake: какие цели (executable/library) есть, какие исходные файлы в них входят, какой стандарт C++ использовать, какие флаги компилятора применить и какие файлы генерировать (например, compile_commands.json).

7. Что означает настройка CMAKE_CXX_STANDARD 20?

Она указывает CMake, что проект должен собираться с использованием стандарта C++20. Компилятор будет проверять синтаксис и возможности языка согласно этому стандарту.

8. Зачем включать CMAKE_EXPORT_COMPILE_COMMANDS?

Чтобы CMake сгенерировал файл compile_commands.json, в котором содержатся точные команды компиляции для каждого .cpp файла. Этот файл нужен для корректной работы языкового сервера clangd (подсказки, переходы, диагностика).

9. Почему clangd зависит от compile_commands.json?

Clangd не может «угадать», как именно компилируется проект. Ему нужны реальные флаги, include-пути, макросы и стандарт языка. Без compile_commands.json подсказки будут неполными или ошибочными.

10. Почему рекомендуется отключать конфликтующий IntelliSense при использовании clangd?

Чтобы два разных движка анализа кода не конфликтовали. Встроенный IntelliSense C/C++ и clangd могут по-разному видеть проект (например, из-за разных путей к заголовкам), что приводит к дублирующимся или противоречивым подсказкам и ошибкам в редакторе.

11. Что делает команда cmake -S . -B build/debug?

Запускает этап Configure: -S . указывает, что исходный код находится в текущей папке, а -B build/debug — что файлы сборки нужно сгенерировать в подкаталоге build/debug (out-of-source build).

12. Чем отличается configure от build в CMake?

Configure анализирует CMakeLists.txt, проверяет наличие компилятора и зависимостей, создаёт правила сборки (файлы в каталоге build). Build — это уже непосредственная компиляция и линковка исходных файлов в исполняемый файл согласно созданным правилам.

13. Почему для отладки нужен режим Debug?

В режиме Debug компилятор добавляет отладочную информацию (символы, связь с исходным кодом) и отключает агрессивные оптимизации. Без этого отладчик (CodeLLDB) не сможет корректно останавливаться на точках останова и показывать значения переменных.

14. Какую роль выполняет CodeLLDB?

Это расширение VS Code, которое связывает редактор с отладчиком LLDB. Оно позволяет запускать программу под отладкой, ставить точки останова, выполнять код по шагам, просматривать стек вызовов и значения переменных.

15. Что проверяет breakpoint?

Он проверяет, что вся инструментальная цепочка связана корректно: исходный код → сборка с отладочной информацией → запуск под отладчиком → остановка в нужном месте. Если breakpoint срабатывает, значит, VS Code, CodeLLDB и собранный бинарник «дружат» между собой.

16. Зачем нужен файл .vscode/launch.json?

Он описывает конфигурацию запуска и отладки для VS Code: какую программу запускать (путь к бинарнику), с какими аргументами, в каком каталоге и с каким типом отладчика (lldb). Без него VS Code не знает, как именно запускать проект в режиме Debug.

17. Зачем нужен .gitignore?

Чтобы исключить из репозитория временные и генерируемые файлы: каталог build/, объектные файлы (*.o), исполняемые файлы, кэш редактора. В Git должны попадать только исходники и настройки проекта, а не артефакты сборки.

18. Что должно попасть в первый commit, а что не должно?

Должно попасть: CMakeLists.txt, src/main.cpp, include/, .devcontainer/, .vscode/, .gitignore, README.md.
Не должно попасть: каталог build/, скомпилированные бинарники, временные файлы, .DS_Store, личные настройки ОС.

19. Какие признаки показывают, что рабочая среда готова к следующей лабораторной работе?

Контейнер открывается без ошибок (Dev Container виден в левом нижнем углу).
CMake configure и build проходят успешно.
Программа запускается и выводит ожидаемый результат.
Breakpoint в Debug-режиме срабатывает.
clangd не показывает критических ошибок (видит compile_commands.json).
В Git есть первый осмысленный коммит.
README содержит инструкцию по сборке и запуску.
